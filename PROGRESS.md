### Junction identified

- **Silk Board Junction, Bangalore** — geocoded to **12.9158171°N, 77.6240368°E** via OSM Nominatim.

### OSM road network fetched (Phase 2)

- Ran `scripts/fetch_osm.py` — first attempt saved `data/osm/silk_board.osm.xml` (726 nodes, 1200 edges) but `osmnx` warned that `all_oneway=True` must be set before fetching for one-way streets (like the flyover ramps at Silk Board) to export correctly to OSM XML.
- Fixed the script to set `ox.settings.all_oneway = True` and re-ran it. Result: **726 nodes, 804 edges**, saved to `data/osm/silk_board.osm.xml` (185 KB) — the drop from 1200→804 edges reflects duplicate bidirectional edges being correctly collapsed into single tagged one-way ways.

### SUMO network built (Phase 2)

- Ran SUMO's `netconvert` to convert the raw OSM XML into an actual SUMO network:
  ```
  netconvert --osm-files data/osm/silk_board.osm.xml \
    --output-file sumo/silk_board/silk_board.net.xml \
    --geometry.remove --roundabouts.guess --ramps.guess \
    --junctions.join --tls.guess-signals --tls.discard-simple --tls.join \
    --osm.all-attributes true
  ```
  - Produced warnings about junction clustering, sharp turn radii, and reduced speeds on tight connections — expected/normal for a complex real-world junction with flyovers and ramps, not errors.
- **Output: `sumo/silk_board/silk_board.net.xml`** (1.6 MB) — the SUMO digital-twin road network for Silk Board Junction. Verified with `sumolib`: **550 edges, 254 nodes, 1 traffic light** (at the main junction).
- This is the core artifact for Phase 2 — the digital twin's road layout is now in place. Still needed to finish Phase 2: traffic demand (routes/flows) calibrated to roughly match the video, once the video is available.

### Widened the road network fetch (Phase 2)

- The first network (600m radius) only had **6 boundary points** (5 entry, 1 sink) — too few and lopsided for realistic multi-directional traffic, since roads within 600m mostly looped back into each other rather than reaching the true edge of the modeled area.
- Increased `RADIUS_M` to **1000m** in `scripts/fetch_osm.py` and re-fetched: **2152 nodes, 2464 edges** in the raw OSM data.
- Rebuilt the SUMO network with the same `netconvert` command as before. New result: **`sumo/silk_board/silk_board.net.xml`** now has **2342 edges, 986 nodes, 1 traffic light**, with **25 boundary points (14 entries, 11 exits)** — enough directional variety to represent Silk Board's real arms (Hosur Road, Outer Ring Road toward Marathahalli, ORR toward BTM/Jayanagar, etc.).

### Synthetic traffic demand generated (Phase 2)

Since no video/manual counts are available yet, generated placeholder demand reflecting Bangalore's real traffic mix so the simulation is drivable end-to-end now. This will be recalibrated once the video is available (per PLAN.md Phase 2).

- **`sumo/silk_board/silk_board.vtypes.xml`** — defines 5 vehicle types with realistic size/speed/behavior parameters for Indian traffic: `motorcycle`, `auto_rickshaw`, `car`, `bus`, `truck`.
- **`scripts/generate_demand.py`** — generates the demand:
  1. Runs SUMO's bundled `randomTrips.py` once per vehicle type, biasing trip origins/destinations toward the network's boundary edges (`--fringe-factor 100`) so trips represent real through-traffic on the junction's arms, not short interior hops.
  2. Mode split modeled on Bangalore's real traffic (motorcycle-dominant): motorcycle 2000 veh/h, car 1200 veh/h, auto-rickshaw 480 veh/h, truck 200 veh/h, bus 120 veh/h — **4000 vehicles/hour total**, reflecting Silk Board's notorious congestion.
  3. Merges all per-mode trips into `sumo/silk_board/silk_board.trips.xml`, sorted by departure time.
  4. Routes them through the real network with SUMO's `duarouter` → **`sumo/silk_board/silk_board.rou.xml`** (the final route file SUMO simulates on). All 4000 trips routed successfully.
  - Bug fixed along the way: the first `duarouter` run didn't know about the custom vehicle types (they weren't passed in), so it fell back to defaults for every vehicle. Fixed by passing `silk_board.vtypes.xml` as an additional file to `duarouter` — it now embeds the correct vType definitions directly into `silk_board.rou.xml`.

### Main SUMO config + first successful simulation run (Phase 2 complete)

- **`sumo/silk_board/silk_board.sumocfg`** — the main SUMO config tying together the network and route files, 1-hour simulation (0–3600s). Run with `sumo -c silk_board.sumocfg` (headless) or `sumo-gui -c silk_board.sumocfg` (visual).
  - Bug fixed: initially also referenced `silk_board.vtypes.xml` as an additional file, which clashed with the vTypes `duarouter` had already embedded in `silk_board.rou.xml` ("Another vehicle type... exists" error). Removed the redundant reference.
- **Ran the full 1-hour simulation headlessly as a sanity check** — it completed successfully:
  - 3,739 of 4,000 vehicles finished their trip within the hour (the rest were still en route when the simulation ended, or teleported after being stuck >300s).
  - Average speed 9.61 m/s (~34.6 km/h), average waiting time 25.64s, average time loss 77.35s per vehicle — numbers consistent with a genuinely congested junction, which is a good sign the digital twin behaves plausibly.
- **Phase 2 (Build the Digital Twin) is now functionally complete** with placeholder demand. Real calibration against video-derived counts is still pending the video.
